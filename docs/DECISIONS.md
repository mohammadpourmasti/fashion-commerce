# Architecture Decision Records

Short records of decisions that are costly to reverse. Add new entries at the
bottom; supersede rather than edit accepted ones.

---

## ADR-001 — Modular monolith on Next.js

**Status:** Accepted · 2026-11-11

**Context:** One team, early product, many domains (catalog, POS, finance, AI).
Microservices would add network, deployment and consistency costs now.

**Decision:** Single Next.js application with business modules under
`src/modules`, each with a public API, declared dependencies and owned data.

**Consequences:** Simple deployment and transactions. Boundaries rely on
discipline plus tooling (ESLint deep-import ban, acyclic graph check). A module
can be extracted later because its API and data are already isolated.

## ADR-002 — Next.js 16.4 with Cache Components

**Status:** Accepted · 2026-11-11

**Decision:** Use the current stable Next.js (16.4.6) as generated by
`create-next-app@16.4.6`, keeping `cacheComponents` and `partialPrefetching`
enabled, with Turbopack.

**Consequences:** Static shells with streamed dynamic parts by default. Some
APIs differ from older Next.js (e.g. `proxy.ts` replaces `middleware.ts`, error
boundaries receive `retry`). Contributors must consult
`node_modules/next/dist/docs/` (see `AGENTS.md`).

## ADR-003 — Sub-path locale routing, Persian default

**Status:** Accepted · 2026-11-11

**Decision:** All pages under `/{locale}` with `fa` (RTL, default) and `en`
(LTR). Locale negotiated in `proxy.ts` (cookie → Accept-Language → default).
Root layout lives at `app/[locale]/layout.tsx` and reads the locale via
`next/root-params`.

**Consequences:** Clean SEO (`hreflang` alternates), static prerender per
locale. Unmatched URLs need `global-not-found.tsx` (experimental flag
`globalNotFound`), which is bilingual because no locale is known there.

## ADR-004 — No i18n library yet

**Status:** Accepted · 2026-11-11

**Decision:** Typed TypeScript dictionaries plus `Intl` for formatting, instead
of `next-intl` or similar.

**Consequences:** Zero dependencies, full type safety. Revisit if we need ICU
plural/select messages at scale or translator tooling.

## ADR-005 — Fonts

**Status:** Accepted · 2026-11-11

**Decision:** Vazirmatn for all Persian text. For Latin: Cormorant Garamond
(display) and Instrument Sans (text). All self-hosted at build time via
`next/font/google`.

**Consequences:** No runtime third-party font requests. Builds need network
access to fetch fonts once; switch to `next/font/local` with committed font
files if builds must run offline.

## ADR-006 — Brand palette with contrast-derived tokens

**Status:** Accepted · 2026-11-11

**Context:** Champagne (#B69A76) on Ivory measures 2.4:1 and Stone (#88847D)
3.4:1 — both below WCAG AA (4.5:1) for body text.

**Decision:** Keep the five brand colours, restrict Champagne to decorative
accents on light grounds (allowed as text on Charcoal, 5.9:1), restrict Stone
to large text/borders, and add a derived `stone-ink` (#66625B, 5.5:1) for small
secondary text. Tailwind's default palette is removed so only brand tokens
exist. No dark mode for the storefront in phase 0.

## ADR-007 — Money as integer minor units; IRR as record, toman as display

**Status:** Accepted · 2026-11-11

**Decision:** `Money = { amountMinor: safe integer, currency }`. IRR is stored
in rials; the UI can display toman (÷10). Prices per currency come from
explicit price lists rather than live conversion. Database columns will be
`bigint`.

**Consequences:** No float rounding errors; IRR amounts stay well within
`Number.MAX_SAFE_INTEGER`. If a currency ever exceeds that range, switch the
type to `bigint`.

## ADR-008 — Environment validated with Zod at boot

**Status:** Accepted · 2026-11-11

**Decision:** `src/config/env.ts` validates public vars at import and server
vars in `getServerEnv()`, called from `instrumentation.ts` at server start.
Variables for unbuilt integrations are optional and become required in their
module's phase.

## ADR-009 — Provider independence via ports

**Status:** Accepted · 2026-11-11

**Decision:** Payments, shipping, storage (S3-compatible API) and AI are
accessed through interfaces owned by their module; providers are adapters.
No real payment provider is connected until explicitly approved.

## ADR-010 — Known dev-dependency advisory

**Status:** Accepted · 2026-11-11

**Context:** `npm audit` reports 7 moderate advisories, all from `minimatch`
inside `typescript-eslint@8.72.2` (pulled in by `eslint-config-next`). The fix
requires a `typescript-eslint` release newer than the latest published one.

**Decision:** Accept for now — lint tooling only, not in the production bundle.
Re-run `npm audit` when `eslint-config-next` or `typescript-eslint` updates.

**Addendum (2026-11-12, phase 2A):** adding `drizzle-kit` (dev only) raised the count
from 7 to 11 moderate advisories, from its bundled `esbuild` 0.18.20. It is used only
to draft SQL locally, never in the runtime or the image. Re-check on each `drizzle-kit` update.

## ADR-011 — Test tooling and versions

**Status:** Accepted · 2026-11-12

**Context:** The latest Vitest (5.x) requires Node ≥ 22.12 and `@types/node`
≥ 22, which conflicts with this project's `engines` (`>=20.9.0`) and
`@types/node` `^20`.

**Decision:** Use Vitest 4.1 (supports Node 20, 22 and 24) for unit tests and
`@playwright/test` for end-to-end tests. Playwright runs against the production
build (`next start`), not the dev server, so tests exercise what ships
(prerendering, `proxy.ts`, `global-not-found`). Unit tests live beside the code
as `*.test.ts`; e2e specs live in `e2e/`.

**Consequences:** Move to Vitest 5 when the minimum Node version and
`@types/node` are raised to 22. CI uses Node 22. The localized-404 e2e tests
are `fixme` until a route calls `notFound()`.

## ADR-012 — Container strategy: opt-in standalone output, Compose for dev

**Status:** Accepted · 2026-11-12

**Decision:** The production image uses Next.js `output: "standalone"`, enabled
only by `NEXT_OUTPUT=standalone` (set in the Dockerfile) so local builds,
`next start` and Windows development are unaffected. Local development uses
Docker Compose for PostgreSQL only (the app itself runs with `npm run dev`),
with a pinned image tag, a named volume, a health check, throwaway credentials
and the port bound to `127.0.0.1`.

**Consequences:** One extra env flag to know about. Server secrets are supplied
at run time and never baked into the image; `NEXT_PUBLIC_*` values are build
arguments. The image build needs network access for Google Fonts (ADR-005);
switch to `next/font/local` if builds must run offline.

## ADR-013 — Phase 2 scope and split

**Status:** Accepted · 2026-11-12

**Decision:** Phase 2 is delivered as 2A data foundation, 2B identity, 2C catalog,
2D inventory, 2E integration. Each sub-phase needs approval before the next

## ADR-014 — Database tooling and migration policy

**Status:** Accepted · 2026-11-12

**Decision:** `drizzle-orm` + `pg`; `drizzle-kit` only drafts SQL. A custom runner
applies `drizzle/NNNN_name/{migration.sql,down.sql}` with SHA-256 checksums
(CRLF normalized), a transaction-scoped advisory lock, `lock_timeout`, and drift
detection. Every migration has a safe `down.sql`: SQL guards `fc_assert_*` raise
`FCD01` instead of dropping data, and production down is blocked unless explicitly
allowed. CI proves the up/down round trip.

**Consequences:** Slightly more tooling than stock drizzle-kit, in exchange for
reviewable SQL and no silent data loss.

## ADR-015 — Data boundaries

**Status:** Accepted · 2026-11-12

**Decision:** Each module owns its tables. Foreign keys point only downstream to
upstream and never to `users`. A module may import another module's schema only
through `schema-refs.ts`, for FK definitions only, enforced by a precise ESLint
rule plus a dependency-direction test.

## ADR-016 — Kernel authorization contracts

**Status:** Accepted · 2026-11-12

**Decision:** Catalog and inventory do not depend on identity. The shared kernel
defines `Actor`, `Permission`, `Scope` and `RequestContext`; identity implements
them and the composition root wires them in.

## ADR-017 — Authentication and sessions

**Status:** Accepted · 2026-11-12

**Decision:** Email + password only. Passwords hashed with scrypt (`node:crypto`).
Sessions use an opaque 256-bit token; only its HMAC is stored. IDs use `uuidv7()`.

*Login throttling:* 5 failures per 15 minutes per account+IP; 100 attempts per hour
per account; delay capped at 15 minutes; no hard account lockout (prevents
lockout abuse). CSRF protection on all state-changing requests.

*Session cookie:*

| | HTTPS (production) | HTTP on loopback (development) |
| --- | --- | --- |
| Name | `__Host-session` | `session` |
| `Secure` | yes | no |
| `Path` | `/` | `/` |
| `Domain` | never set | never set |
| `HttpOnly` | yes | yes |
| `SameSite` | `Lax` | `Lax` |

Loopback means `localhost`, `127.0.0.1` or `[::1]`. We do not rely on browsers
accepting `Secure` cookies on localhost. In production, a non-HTTPS site URL
other than loopback is a startup error (implemented in 2B; not added in 2A
because the Docker and e2e smoke tests run production mode on `http://localhost`).

## ADR-018 — Variant integrity

**Status:** Accepted · 2026-11-12

**Decision:** Links between products, variant axes, attribute values and variants
use composite foreign keys, so a variant can never reference an attribute value
from another product. SKU and barcode are unique.

## ADR-019 — Inventory ledger and reservations

**Status:** Accepted · 2026-11-12

**Decision:** `stock_levels` is a projection of an append-only `stock_movements`
ledger and both change in one transaction.

*Write path (security):* `set_config` or any session setting is **not** a security
mechanism. The application role has `SELECT` only on `stock_levels` and
`stock_movements`, and no `INSERT`/`UPDATE`/`DELETE`. All changes go through
owner-owned `SECURITY DEFINER` functions with a fixed `search_path`; the app role
has only `EXECUTE` on them. 2D must include bypass tests: direct `UPDATE`,
`INSERT` and `DELETE` as the app role are rejected, and `set_config` tricks change nothing.

*Idempotency:* reserve, release, commit and movement logging take an idempotency
key; a repeat returns the original result.

*Delta matrix* (`Δo` = `on_hand` delta, `Δr` = `reserved` delta, `q` > 0):

| kind | Δo | Δr | notes |
| --- | --- | --- | --- |
| receipt | +q | 0 | |
| return | +q | 0 | |
| adjustment | ±q | 0 | |
| damage | −q | 0 | |
| stocktake | ±q | 0 | |
| reserve | 0 | +q | creates an active reservation |
| release | 0 | −q | terminal for the reservation |
| expire | 0 | −q | terminal for the reservation |
| commit | −q | −q | one movement; needs a `reservation_id`; terminal |
| sale (direct POS) | −q | 0 | no reservation; availability enforced by CHECK |

Invariants: `reserved` = sum of quantities of active reservations;
`on_hand` = sum of `Δo`; `reserved` = sum of `Δr`; at most one terminal movement
per reservation (partial unique index), so commit, release and expire can never
both apply. Commit is a single movement, so it is never counted as a release plus a
sale. Partial commit is deferred. Tests are table-driven and run in 2D.

## ADR-020 — Transactional outbox

**Status:** Accepted · 2026-11-12

**Decision:** Domain events are inserted into `outbox_events` in the same
transaction as the business change (`tx.events.add`). The dispatcher claims rows
with `FOR UPDATE SKIP LOCKED`, runs each consumer in a savepoint, and records
`handled_events(consumer, event_id)` so effects are applied once. Failures back off
exponentially (5 s × 2^n, capped at 15 minutes) and dead-letter after 8 attempts.
Delivery is at-least-once; event ordering is not guaranteed.

## ADR-021 — Shared order and currency neutrality

**Status:** Accepted · 2026-11-12

**Decision:** Web and POS share one `orders` table in the commerce module with a
`channel` column. Catalog holds no prices; amounts are integer minor units with an
explicit currency code, and nothing depends on one currency or payment gateway.

## ADR-022 — Identity data model and RBAC (Phase 2B)

**Status:** Accepted · 2026-11-14

**Decision:** Identity owns `users`, `credentials`, `sessions`, `roles`, `permissions`,
`role_permissions`, `user_roles`, `audit_events` and `auth_throttle` (migration
`0002_identity`). No other module has a foreign key to them (ADR-015); `user_roles.granted_by`
and `audit_events.actor_id` are plain values for the same reason.

- Authentication is email + password only (scrypt N=2^15, r=8, p=1 via `node:crypto`, NFKC-normalized, 12 to 128 characters). SMS OTP, OAuth and an admin UI are not part of this phase.
- Authorization is role-based with `"<resource>:<action>"` permissions and an optional scope (`global`, or a `type` + `id` defined by the module that owns the scope). A global grant satisfies any scope; a scoped grant only the same scope. There are no wildcards or hierarchy. Deny by default.
- Roles and permissions are defined in code (`identityCatalog`, merged with other modules' catalogs by `mergeCatalogs`) and synchronised idempotently by `syncAuthorizationCatalog`. They are not seeded by the migration, so its guarded `down.sql` stays usable on a fresh database; once the catalog is synchronised `down` is refused by design (non-empty tables).
- The `owner` role holds every catalog permission, including ones added later (re-sync). The last active owner cannot be disabled or lose the role; changes that could remove an owner are serialised with an advisory lock.
- Modules other than identity never import it. They receive a `RequestContext` and call `ctx.authorize(permission, scope)`; identity implements the `Authorizer` port and the composition root wires it. Grants are read from the database on every check, so role changes and disabling take effect on the next request.
- There is no default account. The first owner is created with `npm run identity:create-admin`, which reads the password without echo (never from argv or environment) and refuses when an active owner exists.

## ADR-023 — Sessions, throttling, audit and CSRF (Phase 2B)

**Status:** Accepted · 2026-11-14

**Decision:**

- **Sessions.** Opaque 256-bit random token; only its HMAC-SHA256 (key derived with HKDF from `AUTH_SECRET`, a separate key per purpose) is stored. Absolute expiry 7 days, idle timeout 8 hours, rotation after 1 hour (new row, old revoked as `rotated`, absolute expiry kept; of two concurrent rotations exactly one wins). Logout, password change (other sessions) and disabling a user revoke sessions.
- **Cookie.** `__Host-session` with `Secure; HttpOnly; SameSite=Lax; Path=/` and no Domain on HTTPS. On loopback HTTP only, a plain `session` cookie without `Secure`. Production refuses to boot with `http` on a non-loopback host (`assertSecureSiteUrl` in `instrumentation.ts`).
- **Throttling.** Per account + address: 5 failures per 15 minutes; per account: 100 attempts per hour. Failures are reserved before the password is checked, so parallel guesses cannot all slip through. Over the limit the wait doubles from 30 seconds up to 15 minutes; refused attempts are not counted; a correct password resets the account + address counter. There is no hard lockout. Keys are HMACs of the email and address; unknown addresses share one bucket. Login always answers `invalid_credentials` for any failure and does equivalent work for unknown accounts.
- **Audit.** `audit_events` is append-only for the application role (SELECT and INSERT only). It stores HMACs of addresses, never passwords, tokens, hashes or raw attempted emails; metadata is capped at 4 KB. Authorization denials are logged best-effort (a failing audit write never changes the decision).
- **CSRF.** Stateless check for non-safe methods: `Sec-Fetch-Site` must be `same-origin` when present, otherwise `Origin`, then `Referer`, must equal the site origin; no evidence means refusal. This phase ships the check (`checkCsrf`) and the service layer only; HTTP routes and UI come later and must call it.

## ADR-024 — Catalog data model and variant architecture (Phase 2C)

**Status:** Accepted · 2026-11-15

**Context:** Women's, children's, accessories and underwear ranges, 500 to 3,000 products at
launch, sold online and in boutiques. Variants combine axes such as size and colour, and inventory
(2D) will reference variants, so variant identity and integrity must hold at database level.

**Decision:** Catalog owns 19 tables in migration `0003_catalog`, unprefixed like identity's:
`categories`, `brands`, `attributes`, `attribute_values`, `products`, `product_categories`,
`product_attribute_values`, `product_axes`, `product_axis_values`, `variants`, `media_assets`,
`product_images`, plus seven translation tables (ADR-025). No prices, no stock, no seed rows.

- *Categories* form a tree (`parent_id`); the top level holds the departments (women, kids,
  accessories, underwear) as data, not as an enum. Depth and cycle checks belong to the application.
- *Attributes* have a `usage` (`variant_axis` or `descriptive`) and a `value_type` (`select`, `text`,
  `number`, `boolean`; axes are always `select`). Axis attributes also have an `axis_kind`
  (`color`, `size`, `other`), which descriptive attributes never have. Each sizing system (women,
  kids, bra, shoes) is its own attribute. Values exist only for `select` attributes.
- *Descriptive values* are typed: one row per selected value (several allowed), or one row per
  product and attribute for `number` and `boolean`; `text` values are localized (ADR-025). A
  composite foreign key ties each row to an attribute of the declared usage and type.
- *Primary category.* `products (id, primary_category_id)` references `product_categories`
  (deferred), so the primary category is always one of the product's categories.
- *Variants* have at most three positional axes. `products.axis_count` (0 to 3) is mirrored on each
  variant and referenced by a composite foreign key, and `value1..value3` reference
  `product_axis_values (product_id, position, value_id)` through constant generated position
  columns. Hence a variant uses only values its product offers, in the right position, one per
  axis (CHECK), and each combination once (`UNIQUE NULLS NOT DISTINCT`); a product without axes has
  exactly one variant. A deferred constraint trigger checks that a product's axes are exactly
  positions `1..axis_count`.
- *Frozen axis structure.* Once a variant exists, `axis_count` cannot change and axes cannot be
  removed or re-pointed (RESTRICT foreign keys). New values can still be added to existing axes, and
  values that no variant or image uses can be withdrawn.
- *SKU and barcode.* SKU is required, uppercase, `^[A-Z0-9][A-Z0-9-]{2,39}$`, unique. Barcode is
  optional, unique, and must be a valid GTIN-8/12/13/14 (`catalog_gtin_is_valid`).
- *No physical deletion of master rows.* The application role has no `DELETE` on products, variants,
  attributes, attribute values, categories, brands or media assets: products go
  draft → active → archived, variants active → discontinued, the rest are archived.
- *Concurrency.* `products.version` supports optimistic locking in the application layer.
- Rules that need application context stay in the application (Step 2 onward): publishing requires
  a Persian translation, at least one active variant and at least one image; category depth and
  cycles; the 100-variant cap; slug normalization. Returnability and similar rules for underwear or
  children's wear belong to commerce. Collections are deferred. `schema-refs.ts` and its lint rule
  arrive with the first consumer (2D). Catalog exports its permission catalog and the composition
  root merges it (2E). Domain events go through the outbox with ID-only payloads.

**Consequences:** Variant integrity does not depend on application code. A fourth axis, or a change
of axes on a product that already has variants, needs a new product (or a deliberate migration).
Some declarations (deferrable constraints, the trigger, the GTIN function) exist only in SQL;
the Drizzle mirror documents them and an integration test checks that they are present.

## ADR-025 — Localized content and image metadata (Phase 2C)

**Status:** Accepted · 2026-11-15

**Decision:**

- *Translations* live in dedicated tables keyed by `(owner, locale)` — categories, brands,
  attributes, attribute values, products, text attribute values and image alt text — not in JSONB.
  `locale` is a two-letter code validated against the configured locales by the application;
  Persian (`fa`) is required to publish, English (`en`) is optional.
- *Slugs* are per locale and unique per `(locale, slug)` for categories, brands and products. They
  are normalized Persian script, not transliteration: lowercase Latin letters, ASCII digits and
  Persian letters, with Arabic yeh/kaf mapped to Persian ی/ک, no ZWNJ or spaces, and words joined by
  single hyphens (at most 160 characters). The database rejects anything else; the application
  produces the normalized form.
- *Images.* `media_assets` holds metadata only (storage key, content type JPEG/PNG/WebP/AVIF, size,
  dimensions, SHA-256); storage and upload come later. `product_images` places an asset on a
  product with a `view` (`front`, `back`, `detail`, `gallery`) for the future digital clothing rack,
  a position (unique per product, deferred so images can be reordered), and an optional colour
  link: `(color_value_id, color_attribute_id)` must be a value this product offers, and the attribute
  must have `axis_kind = 'color'`. Size values and values of any other axis are rejected, and a
  colour attribute referenced by images cannot change its kind.
  3D assets and virtual try-on are out of scope.

**Consequences:** Adding a locale needs no migration. Persian-script slugs are percent-encoded in
URLs, and browsers display them readably. A new image view needs a migration that widens the CHECK.

## ADR-026 — Catalog domain rules (Phase 2C)

**Status:** Accepted · 2026-11-15

**Context:** ADR-024 and ADR-025 leave rules that need application context to the domain layer.
Step 2 implements them as pure functions in `src/modules/catalog/domain`, with no database access.

**Decision:**

- *Validation style.* Domain functions never throw for bad input; they return
  `Validation<T>` (`{ ok: true, value }` or `{ ok: false, issues }`) listing every issue with a
  stable code and a path, so a form can show all problems at once.
- *Slugs* (`slugify`): NFKD with Latin accents removed, then NFC; Arabic yeh/alef maksura/kaf/heh-yeh/teh
  marbuta mapped to Persian ی/ک/ه, hamza and wasla letters folded to their base letter, Arabic
  diacritics and tatweel removed, Persian and Arabic-Indic digits converted to ASCII, ZWNJ, other
  zero-width and bidi control characters, spaces and punctuation turned into single hyphens, cut at a word boundary at 160 characters. Display
  text keeps ZWNJ and the digits the author typed.
- *One colour axis per product.* A product may have at most one axis whose attribute has
  `axis_kind = 'color'`. Enforced in the domain (`planAxes`), not in the database: images already
  link to a specific colour attribute and value, so a second colour axis would not corrupt data.
- *Lifecycle:* draft → active (publish), active → draft (unpublish), draft or active → archived
  (archive), archived → draft (restore). Publishing requires a Persian translation, an active
  primary category, an active brand when one is set, all declared axes, at least one active variant
  and at least one image.
- *Categories:* at most four levels; a move takes the whole subtree, may not create a cycle and may
  not push any descendant below level four; parents must be active.
- *Variants:* at most 100 per product, counting discontinued ones (variants are never deleted);
  matrix generation refuses a matrix larger than that. SKUs are trimmed, upper-cased and Persian
  digits converted; barcodes lose spaces and hyphens before the GTIN check.
- *Descriptive values:* each attribute at most once per product; select attributes may hold several
  values (no single-select flag yet); numbers must fit `numeric(14, 4)` exactly and are never
  rounded; archived attributes and values cannot be newly assigned, but a product may keep an
  archived value it already has.
- *Parity.* Patterns in the domain mirror the 0003 CHECK constraints; an integration test runs both
  on the same inputs and fails on any disagreement.

**Consequences:** Application services (Steps 3–7) only orchestrate: load state, call these
functions, write in one transaction with outbox events. A future single-select attribute needs a
schema flag and a domain rule.
